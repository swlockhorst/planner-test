# Code Factory — Project Template

A reusable foundation for building software applications using an AI-assisted development factory.

The Code Factory combines specialized AI agents with deterministic automation to plan, implement, validate, and release software.

## Core Principle

**Use AI for work requiring reasoning, interpretation, creativity, or judgment. Use deterministic code for operations that can be reliably defined, validated, and executed through conventional programming.**

The factory prioritizes simplicity, reliability, predictable execution, and efficient AI usage.

## Getting Started

### 1. Create a Repository

On GitHub, select **Use this template → Create a new repository**.

Name the repository after the application you're building.

For an existing repository, copy the `.factory/` configuration into it instead.

### 2. Create a Claude Planner Project

Create a new Claude Project dedicated to your application.

Example: `My Application — Planner`

Configure its Project Instructions to follow `.factory/planner/instructions.md` and use the document templates in `.factory/planner/templates/`.

Connect the application repository to Claude with the appropriate permissions.

Keep project memory isolated from unrelated applications.

### 3. Plan Your First Release

Start a conversation with your Planning Agent.

The Planner collaborates with you to define the release and produce:

- **PRD** — Required product requirements.
- **Design Specification** — Optional, determined by the human.
- **Architecture Specification** — Optional, determined by the human.
- **Holdout Scenarios** — Required private QA evaluations.

The Planner must receive explicit human approval before handing off a release.

### 4. Factory Handoff

The intended automated planning pipeline is:

1. Human approves release specifications.
2. Approved planning documents are published to GitHub.
3. The Decomposition Agent creates `tasks.yaml`.
4. The Planning Review Agent validates the task breakdown.
5. Deterministic automation creates GitHub issues and dependency relationships.

Cloud handoff automation must be configured before this pipeline can execute automatically.

## Repository Structure

```text
.factory/
├── planner/
│   ├── instructions.md
│   └── templates/
│       ├── prd-template.md
│       ├── design-template.md
│       ├── architecture-template.md
│       └── holdout-template.md
└── releases/
    └── .gitkeep
```

Each release receives its own directory:

```text
.factory/releases/release-001/
├── prd.md
├── design.md          # Optional
├── architecture.md    # Optional
├── tasks.yaml         # Generated by decomposition
└── manifest.json      # Release metadata
```

## Security

Populated holdout scenarios must never be committed to the application repository.

Store them in a separate, access-controlled location inaccessible to coding agents.

Only approved planning documents should be used as the authoritative input for task decomposition.

## Project Conventions

- Each application has its own repository and Claude Planner Project.
- Each release has a unique identifier.
- PRD requirements use stable identifiers such as `REQ-001`.
- All planning documents must be approved before automated handoff.
- One `tasks.yaml` file is generated per release.
- GitHub Issues become the execution queue after publication.
- AI agents perform reasoning; conventional code handles deterministic orchestration and API operations.
